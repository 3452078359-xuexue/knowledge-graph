# 曼谷酒店入住平台现状、采集方法与问题

版本：v1.0  
更新时间：2026-09-07  
数据范围：曼谷 Google Maps 酒店“所有选项”平台关系、官网预订引擎和隔离详情采集结果

## 1. 结论先行

当前体系已经可以批量获取 Google Maps 酒店的“所有选项”平台入口，并以 CSV 形式保存酒店 ID、平台名称、是否官网和 URL。详情层已经验证出少量平台可以解析房型或售卖方案，但还没有任何平台通过完整的 T4 人工审核，因此当前可稳定每日批量采集并发布到正式比价层的平台数量是 **0 家**。

这几个数字必须区分：

| 指标 | 当前数量 | 口径 |
|---|---:|---|
| Google Maps 酒店 | 1,273 家 | 曼谷酒店主数据唯一酒店 ID |
| 住宿分类 | 30 类 | 主数据 `住宿类型` 字段 |
| 原始平台展示名称 | 231 个 | Google Maps “所有选项”原始文本 |
| 标准化平台 | 67 家 | 按平台注册表归并后的对象，不等于 67 个独立价格源 |
| 酒店—平台关系 | 6,014 条 | 正式四列关系 CSV |
| 已覆盖平台入口的酒店 | 490 家 | 1,273 家中的 490 家 |
| 暂无正式平台关系的酒店 | 783 家 | 只表示当前未取得平台关系，不表示确认没有平台 |

## 4. 使用的方法

### 4.1 Google Maps 平台发现

1. 读取曼谷酒店主数据中的 Google Maps 酒店 ID。
2. 打开价格区域，读取“所有选项”列表；“精选选项”只作为页面展示子集，不能代替完整平台列表。
3. 提取每个入口的酒店 ID、平台展示名称、是否官网和 URL。
4. 按 `酒店ID + 平台名称` 去重，保留最适合进入详情页的 URL。
5. 将原始展示名称匹配到平台注册表，生成标准平台 ID、平台类型、同源组和采集通道。

正式关系表固定为四列：

```text
酒店ID,酒店入住平台名称,是否官网,URL链接
```

Google Maps `pid` 不写入正式关系表。用户提供的 `pid:ChIJW2suuOCZ4jARn5DZfMSQDSI` 只属于检索或页面定位辅助信息，不作为正式酒店 ID。

### 4.2 URL 和平台酒店身份

平台入口先经过 URL 解析，再判断是否落到目标酒店详情页。处理顺序为：

1. 跟随重定向和 Meta 中转。
2. 根据平台适配器提取 `hotel_id`、`dest_id`、`hotelId`、`hid`、`selected` 或平台特有编码。
3. 写入住店日期、离店日期、成人数、房间数和币种。
4. 区分搜索页、列表页、酒店详情页和帮助/机器人页面。
5. 只有目标酒店身份和详情层级足够明确，才允许进入房型解析。

### 4.3 房型和售卖方案

每个详情任务独立保存：

- 最终详情 URL
- 平台酒店 ID
- 房型 ID、房型名称、床型、面积、人数、库存等
- 售卖方案 ID、早餐、取消政策、支付方式、价格、币种、税费和计价单位
- 原始页面或接口快照
- 采集状态、失败原因和采集时间

通用采集器负责公共流程，平台适配器负责日期参数和页面结构；动态官网引擎使用专用适配器。当前代码位置：

`05_GoogleMaps曼谷酒店专用/99_采集程序/曼谷酒店平台详情.py`

已经使用的适配方式包括：

- 常规 OTA 详情页 DOM / 内嵌 JSON 解析
- 重定向和 Meta 搜索中间页解析
- Booking.com Apollo 页面缓存房型回退解析；该回退只提取房型，不把页面数字当作价格
- OWNLY 同源公开接口采集
- AceMS 浏览器内短期 token + 公开预订接口采集；token 不写入 CSV
- HotelRunner 日期字段适配器；当前只完成入口规则，房态接口仍待继续适配
- 1HotelRez 公开预订引擎：先读取指定日期入口的服务端房型 DOM；无房型时再调用同源 `select.room.list.php` 房态接口。对 `Not Available`、重复方案和 “Book Now THB 0” 做了排除，不把不可售提示误写成零价格
- Travelanium `propertyibe2` 入口识别：已进入专用适配分支，但遇到 Cloudflare 人机验证即停止，不尝试绕过

### 4.4 批量和质量控制

- 平台发现按酒店 ID 分片，并优先处理未覆盖或失败待重试酒店。
- 详情任务按平台/引擎隔离；一个平台失败不能清空其他平台的有效检查点。
- 浏览器断开时重建会话并只重试当前任务一次。
- 失败、超时、登录/验证码和未解析房型都保留在状态 CSV，不把失败写成“确认无平台”。
- 房型、售卖方案和正式可比价格分层落盘。
- T4 采用多酒店、两组日期、两次独立会话；平台和价格语义必须人工审核后才能放行。
- 当前阶段只输出 CSV 和压缩原始留档，不创建 SQLite。

## 5. 当前主要问题

### 5.1 平台入口覆盖不完整

当前 1,273 家酒店中只有 490 家取得正式平台入口，783 家没有正式关系。无关系酒店可能是页面超时、价格区域未加载、Google Maps 没有返回结果，或者官网/第三方入口尚未完成身份核验，不能直接理解为“酒店没有售票平台”。

官网补采候选和备用平台候选使用独立队列，避免将未核验链接污染正式四列关系表。

### 5.2 精选选项与所有选项混淆

Google Maps 的“精选选项”只展示部分平台，可能包含房型或优惠展示；“所有选项”才是当前平台发现的完整入口来源。任何只读取精选区域的程序都会漏掉 EaseMyTrip、Stayforlong、Agoda、klook、Tiket 等其他入口。

### 5.3 URL 可达不等于房价可得

当前详情状态共 199 条、涉及 41 个适配器，状态分布为：

| 状态 | 数量 |
|---|---:|
| 采集成功 | 26 |
| 页面未解析到房型 | 131 |
| 需要登录或人工验证 | 28 |
| 房型已采集但售卖方案未解析 | 7 |
| 处理失败 | 7 |

常见情况是 URL 能打开、甚至能取得房型结构，但价格接口没有返回，或价格被登录、日期选择、折叠面板和异步请求隐藏。因此房型数不能替代售卖方案数，页面中的营销数字、押金、税费或原价也不能自动当作当前房价。

### 5.4 动态引擎和平台结构差异

同一个官网可能使用 OWNLY、AceMS、HotelRunner、Travelanium、Cloudbeds、DerbySoft、Triptease 或自建引擎。静态首页、iframe、Angular/Next.js 壳页面通常没有完整房态，必须按引擎观察网络接口或页面状态开发适配器。

HotelRunner 就是当前典型问题：公开 `store` 信息可以取得，但最小房态请求返回 `reset`，浏览器 DOM 只有应用壳，通用解析器自然得到 0 个房型。

### 5.5 反爬、登录和人工验证

平台注册表当前有 51 家可达性标记为 open、2 家 partial、7 家 login/captcha、1 家 robots_denied、6 家 unknown。实际页面还会出现地区、语言、频率、无登录会话和二次验证差异。

当前不绕过验证码、登录墙或 robots 限制；这些入口要么进入人工核验队列，要么改走官方 API、合作接口或元搜索探针。

### 5.6 价格语义和税费口径

必须同时确认：

- 是每晚价还是整个住宿窗口总价；
- 币种和汇率日期；
- 税费是否包含；
- 早餐、押金、服务费是否包含；
- 取消政策和付款节点；
- 日期和入住人数是否与采集任务一致。

当前大量数字价格仍未完成这些语义确认，所以正式 `可比价格.csv` 保持 0 条是预期的质量门禁结果。

## 7. 下一步建议

1. 先完成人工审核 Trip.com 和 Vio.com 的 40 条 T4 证据；两者已经达到 3 家候选酒店基线，但尚未放行。
2. 对 783 家无平台关系酒店继续使用明确酒店 ID 的增量队列，避免全量强制刷新造成已有关系收敛风险。
3. 按官网预订引擎而不是按酒店首页开发规则，优先继续 Travelanium、Cloudbeds、HotelRunner 等高复用引擎。
4. 对已有房型但无售卖方案的平台，优先补日期、价格接口和税费语义；不要仅扩大房型数量。
5. 对白标联盟按同源组选择代表平台，对元搜索只做覆盖探针，减少重复采集。
